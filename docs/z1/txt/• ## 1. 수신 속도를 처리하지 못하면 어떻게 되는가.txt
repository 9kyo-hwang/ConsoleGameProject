• ## 1. 수신 속도를 처리하지 못하면 어떻게 되는가?

  먼저 “수신 버퍼”를 구분해야 합니다.

  송신 애플리케이션 queue
  → 송신 OS socket buffer
  → 네트워크
  → 수신 OS socket buffer
  → recv/WSARecv용 임시 buffer
  → 애플리케이션 framing·message queue

  recv()에 넘기는 4KB 배열은 전체 수신량 제한이 아닙니다. 4KB 버퍼를 반복해서 사용하면 1GB 스트림도 받을 수 있습니다.

  지속적으로 들어오는 속도가 처리 속도보다 빠르면 다음 순서로 밀립니다.

  1. 애플리케이션이 recv()를 충분히 호출하지 못함
  2. 수신 측 OS socket buffer가 차오름
  3. 수신 측 TCP가 advertised receive window(rwnd)를 줄임
  4. 가득 차면 zero window를 광고
  5. 송신 측 TCP가 추가 전송을 멈춤
  6. 송신 측 socket buffer와 애플리케이션 send queue가 밀림

  즉, TCP 자체는 곧바로 연결을 끊기보다 backpressure를 걸어 송신자를 느리게 만듭니다.

  그 결과는 상황에 따라 달라집니다.

  - 잠깐 밀림: 지연만 증가하고 회복
  - 계속 밀림: 패킷이 오래된 상태가 되어 렉 발생
  - 송신 queue가 무제한: 서버 메모리 증가
  - queue 상한 존재: 애플리케이션 정책에 따라 drop, coalesce 또는 연결 종료
  - heartbeat 제한 초과: 애플리케이션이 timeout으로 연결 종료

  MMORPG 서버는 일반적으로 느린 세션 하나가 서버 전체에 영향을 주지 않도록:

  - 세션별 send queue 크기 제한
  - 최신 위치·상태 패킷 coalescing
  - 중요하지 않은 업데이트 생략
  - 초당 입력 패킷 rate limit
  - 일정 시간 이상 밀린 세션 종료

  같은 정책을 둡니다.

  Z1에서는 느린 수신 클라이언트의 서버 send queue가 64개에 도달하면 Session::Send() (Z1Server/Session.cpp:76)이 실패하고 Session을 닫습니다. 이것은 TCP가 자동으로 끊는 게 아니라 Z1 애플리케이션이 선택한 보호 정책입니다.

  반대로 Z1 서버의 4KB _recvBuffer (Z1Server/Session.h:57)는 한 번의 WSARecv 작업 공간입니다. 4KB보다 많은 정상 스트림은 여러 completion으로 나눠 받고 PacketFramer가 이어 붙입니다.

  ## 2. TCP segment가 중간에 유실되면?

  TCP 계층에서 자동으로 복구합니다. 애플리케이션의 NetworkClient나 PacketFramer가 직접 유실 패킷을 처리하지는 않습니다.

  예를 들어 TCP byte 구간이 다음처럼 전송됐다고 해보겠습니다.

  [0~999] [1000~1999] [2000~2999]
             유실

  수신 측은 [2000~2999]가 먼저 도착해도 애플리케이션에 순서가 뒤바뀐 stream으로 전달하지 않습니다.

  TCP는 대략 다음 절차를 수행합니다.

  1. TCP sequence number로 빠진 byte 구간을 확인
  2. 마지막으로 연속 수신한 위치를 ACK
  3. 활성화되어 있다면 SACK으로 나중 구간은 받았다고 알림
  4. 송신 측이 중복 ACK 또는 재전송 타이머로 유실 감지
  5. [1000~1999]를 재전송
  6. 빠진 구간이 채워지면 순서대로 애플리케이션에 전달

  애플리케이션이 관찰하는 결과는 보통 다음 중 하나입니다.

  - 정상적인 순서의 byte stream이 조금 늦게 도착
  - 복구가 오래 걸려 recv()가 오랫동안 완료되지 않음
  - 끝내 복구하지 못하면 timeout이나 socket 오류로 연결 종료

  TCP는 이후 데이터가 이미 도착했더라도 빠진 앞부분이 복구될 때까지 애플리케이션 전달이 막힐 수 있습니다. 이를 head-of-line blocking이라고 합니다.

  게임 입장에서는 유실 자체보다 이 재전송 대기가 “렉”으로 느껴집니다.

  또한 TCP는 애플리케이션 패킷 경계를 모릅니다.

  C2S_Input 하나가 유실됐다

  라고 판단하는 것이 아니라:

  TCP byte stream의 특정 sequence 구간이 빠졌다

  라고 판단합니다. 그 byte가 복구된 다음에야 Z1의 PacketFramer가 완성된 C2S_Input을 조립할 수 있습니다.

  ## 3. 이것이 TCP 혼잡 제어와 이어지는가?

  이어지지만 세 개념을 구분해야 합니다.

   기능                보호 대상                 핵심 값
  ━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━
   신뢰성·유실 복구    유실된 byte               sequence, ACK, 재전송
  ──────────────────  ────────────────────────  ─────────────────────────
   흐름 제어           느린 수신자               receive window, rwnd
  ──────────────────  ────────────────────────  ─────────────────────────
   혼잡 제어           과부하된 네트워크 경로    congestion window, cwnd

  실제 송신 가능한 데이터의 양은 개념적으로 다음 양쪽 제한을 받습니다.

  전송 가능량 ≈ min(rwnd, cwnd)

  - rwnd가 작음: 수신 애플리케이션이 데이터를 빨리 소비하지 못함
  - cwnd가 작음: 네트워크 경로가 혼잡하다고 판단됨

  TCP segment 유실은 혼잡 제어의 중요한 신호이기도 합니다.

  segment 유실
  → 중복 ACK 또는 timeout
  → 재전송
  → 네트워크가 혼잡할 가능성이 있다고 판단
  → cwnd 감소
  → 송신 속도 감소

  즉, 2번의 유실 복구는 “빠진 데이터를 다시 보내는 기능”이고, 혼잡 제어는 “앞으로 보내는 속도를 낮추는 기능”입니다. 같은 유실 사건을 계기로 함께 작동할 수 있지만 목적은 다릅니다.

  정리하면:

  게임이 데이터를 늦게 읽음
  → 흐름 제어(rwnd 감소)

  네트워크 중간에서 segment가 유실됨
  → 신뢰성 처리로 재전송
  → 혼잡 신호로 판단되면 cwnd 감소

  앞 segment가 유실됨
  → 뒤 데이터까지 애플리케이션 전달 대기
  → 게임에서 렉으로 관찰

  그래서 실시간 게임에서는 TCP를 쓰더라도 “전송됐으니 최신 상태가 곧 도착한다”고 가정하면 안 됩니다. 오래된 Snapshot이 send queue에 누적되지 않도록 coalescing하거나, 지나치게 뒤처진 세션을 정리하는 애플리케이션 정책이 별도로 필요합니다.
