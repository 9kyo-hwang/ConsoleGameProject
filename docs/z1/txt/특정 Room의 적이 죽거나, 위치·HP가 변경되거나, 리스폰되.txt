특정 Room의 적이 죽거나, 위치·HP가 변경되거나, 리스폰되면 그 Room을 보고 있는 모든 Player에게 그 결과가 전파되어야 합니다. 이것은 서버 상태를 Room마다 따로 갖는다는 뜻은 아닙니다. 서버는 전역적으로 Enemy를 한 번만 보유하고, Room은 다음 두 판단에 쓰면 됩니다.

  Enemy의 실제 상태
    └─ 서버 전역 레지스트리에서 단 하나만 관리

  Enemy가 속한 homeRoom
    ├─ 그 Room에 Player가 있으면 Enemy Tick
    └─ 그 Room에 관심 있는 Player에게만 상태 전송

  Z1의 첫 구현이라면, 매 Tick에 Player 좌표로 occupiedRooms를 계산하고 다음처럼 처리하는 구성이 가장 단순합니다.

  // 서버의 진실: Enemy는 항상 전역 컨테이너에 존재.
  std::unordered_map<uint32_t, ServerEnemy> _enemies;

  // 매 simulation tick
  const auto occupiedRooms = CollectOccupiedRoomsFromPlayers();

  for (ServerEnemy& enemy : _enemies)
  {
      if (!occupiedRooms.contains(enemy.homeRoom))
          continue; // 상태는 보존하고 Tick만 생략

      enemy.Tick(/* 해당 Room의 Player들 */);
  }

  // 전송 시에는 해당 Player가 관심 있는 Room의 객체만 패킹한다.
  for (Session& session : _sessions)
  {
      const RoomCoordinate room = GetRoomCoordinate(session.player.position);
      SendSnapshot(session, BuildRoomSnapshot(room));
  }

  현재 Snapshot 기반 Z1에서는 Rookiss처럼 꼭 S_AddObject, S_RemoveObject를 별도 패킷으로 만들 필요는 없습니다. 해당 Room Snapshot에 Enemy가 있으면 생성/갱신하고, 이전 Snapshot에는 있었는데 이번에 없으면 클라이언트가 제거하면 됩니다. 사망 연출·사운드처럼 “한 번만 반드시 재생”할 사건이 생길 때만 별도 이벤트 패킷을 추가하면 됩니다.

  한 Room에 Player가 극단적으로 몰리면 느려질 가능성은 있습니다. 병목은 세 곳입니다.

  - 네트워크: 같은 Room 상태 패킷 크기를 B, 초당 전송 횟수를 T, 수신 Player 수를 P라 하면 송신량은 대략 B × T × P입니다.
  - 시뮬레이션: 적이 매 Tick마다 대상 Player를 찾으면 단순 구현은 대략 Enemy 수 × Player 수만큼 비교합니다.
  - 클라이언트: 한 화면/Room에 다수 Player와 투사체가 몰리면 렌더링과 Snapshot 보정 비용도 증가합니다.

  하지만 현재 Z1의 소규모 월드와 Room당 적 수 기준에서는 우선 과도하게 최적화할 단계는 아닙니다. 첫 단계는 “Room의 상태 패킷을 한 번 만들고, 해당 Room의 모든 Session에 재사용해 보낸다”면 충분합니다. 다만 현재처럼 20Hz 전체 Snapshot을 보내는 구조에서 한 Room에 수십~수백 명이 실제로 모이기 시작하면, 다음 순서로 확장하면 됩니다.

  1. Room별 관심 대상에게만 전송
  2. 매 Snapshot 전체 상태 대신 변경분(delta) 전송
  3. Enemy의 대상 탐색을 Room 내 Player 목록으로 제한
  4. 필요할 때만 Room/지역별 simulation worker 또는 shard 고려

  결론적으로, “Room의 모든 Player에게 브로드캐스트”는 맞지만, Room은 전역 상태의 소유자가 아니라 시뮬레이션과 복제 대상 선정용 인덱스로 두는 편이 현재 정책에 가장 잘 맞습니다.
