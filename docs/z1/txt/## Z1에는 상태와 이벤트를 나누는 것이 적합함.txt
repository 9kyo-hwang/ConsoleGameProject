## Z1에는 상태와 이벤트를 나누는 것이 적합함

  Z1은 애니메이션이 없고 공격·사운드가 대부분 단발성이므로 Rookiss의 SKILL 지속 상태보다 다음 구분이 더
  잘 맞습니다.

  ### 지속 상태: Snapshot

  현재 상태를 복구할 수 있어야 하는 값입니다.

  - Player·Enemy 위치
  - facing
  - HP
  - dead
  - 현재 존재하는 Projectile

  이 값들은 지금처럼 S2C_WorldSnapshot으로 보냅니다.

  ### 단발 사건: Event

  한 번만 표현해야 하는 사건입니다.

  - Player SwordSwing
  - PlayerDamaged
  - PlayerDied
  - EnemyDamaged
  - EnemyDied
  - ShieldBlocked
  - ProjectileFired
  - ItemAcquired
  - BossEncountered

  이런 값은 별도의 S2C_GameEvent 또는 더 작은 S2C_CombatEvent로 보내는 것이 자연스럽습니다.

  enum class CombatEventType : std::uint8_t
  {
      PlayerSwordSwing,
      PlayerDamaged,
      PlayerDied,
      EnemyDamaged,
      EnemyDied,
      ShieldBlocked
  };

  struct CombatEvent
  {
      std::uint32_t eventId = 0;
      CombatEventType type{};
      std::uint32_t sourceId = 0;
      std::uint32_t targetId = 0;
      MoveDirection direction = MoveDirection::None;
  };

  서버는 공격 입력을 그대로 재전송하지 않습니다.

  C2S_Input: A 입력
  → 서버가 공격 가능 여부 확인
  → 공격 승인 및 Sword AABB 판정
  → CombatEvent(PlayerSwordSwing) 브로드캐스트
  → 필요하면 EnemyDamaged/EnemyDied 이벤트 브로드캐스트

  클라이언트는 이벤트를 받아 각자 표현합니다.

  switch (event.type)
  {
  case CombatEventType::PlayerSwordSwing:
      SpawnSwordVisual(event.sourceId, event.direction);
      Engine::Get().PlayOneShot("Z1/LOZ_Sword_Slash.wav");
      break;

  case CombatEventType::PlayerDamaged:
      Engine::Get().PlayOneShot("Z1/LOZ_Link_Hurt.wav");
      break;

  case CombatEventType::PlayerDied:
      Engine::Get().PlayOneShot("Z1/LOZ_Link_Die.wav");
      break;

  case CombatEventType::EnemyDied:
      Engine::Get().PlayOneShot("Z1/LOZ_Enemy_Die.wav");
      break;
  }

  이벤트는 사건이 발생한 Room을 관심 영역으로 가진 Session들에게만 Broadcast하면 됩니다.

  ## Snapshot 변화로 충분한 사건은 그대로 사용 가능

  모든 효과를 이벤트로 만들 필요는 없습니다.

  Player Hurt/Die처럼 상태 전이만으로 정확히 알 수 있는 것은 Snapshot 비교로도 충분합니다.

  if (!wasDead && isDead)
  {
      PlayDieSound();
  }
  else if (newHp < previousHp)
  {
      PlayHurtSound();
  }

  이 코드를 MyPlayer가 아니라 공통 NetworkPlayer에 두면 각 클라이언트에서 모든 Player의 피격·사망 사운드
  - 서버가 공격을 승인한 정확한 시점을 표현해야 함

  ## Z1에 추천하는 결론

  Snapshot
  - 위치, HP, dead, Projectile 존재
  - 게임 상태의 원본

  CombatEvent
  - 검 휘두르기
  - 피격·사망 이펙트와 정확한 OneShot
  - 방패 방어
  - 이후 필요한 단발 전투 표현

  Rookiss는 SKILL 상태를 S_Move로 브로드캐스트해 공격 애니메이션을 공유합니다. 사운드와 권위형 피해 동기
  화는 해당 프로젝트에 구현돼 있지 않습니다.

  ## 범용 이벤트 시스템 전체를 만들 필요는 없음

  이번에 아이템·보스·방패까지 한꺼번에 설계하면 작업이 커집니다. 첫 구현은 전투에만 한정하는 것이 좋습니
  다.

  enum class CombatEventType : std::uint8_t
  {
      PlayerSwordSwing,
      PlayerDamaged,
      PlayerDied
  };

  struct CombatEvent
  {
      CombatEventType type{};
      std::uint32_t sourceId = 0;
      std::uint32_t targetId = 0;
      MoveDirection direction = MoveDirection::None;
  };

  첫 vertical slice의 범위는 다음 정도입니다.

  C2S_Input Attack
  → 서버 TryHitEnemy()
  → S2C_CombatEvent(PlayerSwordSwing)
  → 같은 Room Session에 Broadcast
  → 각 클라이언트가 검 Sprite 생성
  → Slash PlayOneShot
  → 클라이언트 Timer로 Sprite 제거

  Player가 Projectile에 맞으면:

  서버 TryHitPlayer()
  → HP 감소
  → PlayerDamaged 또는 PlayerDied Broadcast
  → 각 클라이언트가 Hurt/Die PlayOneShot

  HP와 dead 값은 여전히 Snapshot이 원본입니다. 이벤트는 표현을 트리거할 뿐 게임 상태를 변경하지 않습니
  다.

---

  ## 중요한 구현 특성

  Snapshot과 달리 CombatEvent는 “최신 하나”만 남기면 안 됩니다.

  SwordSwing
  PlayerDamaged
  PlayerDied

  가 한 프레임에 들어왔다면 세 이벤트를 모두 순서대로 처리해야 합니다.

  따라서 클라이언트에서는:

  - Snapshot: 최신 값 하나만 보관 가능
  - CombatEvent: queue에 모두 보관하고 한 번씩 소비

  로 구분해야 합니다.

  TCP를 사용하므로 별도 재전송·ACK 시스템까지 만들 필요는 없습니다. Session의 기존 send queue를 그대로
  사용하면 됩니다.
