  서버 하나에 연결하고, 20Hz 정도의 가벼운 패킷을 처리하는 클라이언트라면 Rookiss처럼 메인 스레드에서 논블로킹 polling을 해도 충분했을 겁니다. 그랬다면 다음 요소들이 사라졌겠죠.
  - _stopRequested, _connected atomic
  - 네트워크 스레드 생성과 join
  - 송수신 큐와 mutex
  - IncomingMessage를 통한 스레드 간 전달
  - 종료 시 큐와 pending 상태 정리
  - 네트워크 스레드 종료와 게임 종료 사이의 상태 관리

  다만 억지로 사후 정당화할 필요는 없습니다. 당시 선택을 가장 정직하게 설명하면 이 정도입니다.

  > CraftEngine의 프레임 루프에 네트워크 갱신 지점을 추가하지 않고도 소켓 수신을 게임 프레임과 독립적으로 처리하기 위해 NetworkClient에 전용 스레드를 두었다. 네트워크 스레드는 소켓 I/O와 패킷 검증까지만 담당하고, 게임 상태와 Actor 변경은 typed message queue를 통해 메인 스레드에서 수행하도록 경계를 분리했다.

  이 설명에는 실제 근거가 있습니다.
  - 수신 처리가 느린 프레임에 종속되지 않음
  - select()에서 일정 시간 대기할 수 있음
  - NetworkThread가 Actor나 Level을 직접 건드리지 않음
  - 게임 스레드와 네트워크 스레드의 책임이 명확함
  - 이후 IOCP나 더 지속적인 네트워크 처리로 확장할 때 구조적 기반이 있음

  하지만 동시에 다음 한계를 인정하면 됩니다.
  > 현재처럼 단일 서버 연결과 가벼운 패킷만 처리하는 MVP에서는 메인 스레드 논블로킹 polling도 충분한 대안이었다. 전용 스레드는 처리량 때문에 필수였던 것이 아니라, 네트워크 I/O를 게임 루프에서 격리하는 방향을 먼저 선택한 결과다.

  이게 오히려 납득 가능한 설명입니다. “성능 때문에 반드시 필요했다”거나 “언리얼도 이렇게 하니까”라고 과장하면 현재 코드 규모와 맞지 않지만, 격리와 명시적인 main-thread 적용 경계를 선택했다는 설명은 코드와 일치합니다.

  언리얼과의 비유도 완전히 엉뚱했던 건 아닙니다. 개념적으로는 다음 부분이 비슷합니다.

  네트워크 계층
      → raw I/O와 packet 처리
  게임 스레드
      → 수신 결과를 gameplay state에 반영

  다만 “FSocket을 사용한다”는 사실만으로 전용 스레드가 따라오는 것은 아닙니다. FSocket을 게임 스레드에서 nonblocking polling할 수도 있고, 별도 worker에서 처리할 수도 있습니다. 즉, 언리얼에서 가져온 것은 소켓 API 사용 방식이라기보다 네트워크와 gameplay state를 분리한다는 막연한 방향성에 가까웠던 셈입니다.

  그리고 이번에 드러난 중요한 한계도 있습니다. 지금 전용 스레드는 연결이 완료된 뒤의 송수신만 담당하므로, Start() (Z1/Network/NetworkClient.cpp:57)의 블로킹 connect()로 인한 타이틀 정지는 막아주지 못합니다. 따라서 “게임 스레드가 네트워크 때문에 절대 블로킹되지 않도록 만들었다”는 설명은 정확하지 않습니다.

  제가 지금 선택한다면 이렇게 판단하겠습니다.
  - 현재 구조가 안정적으로 동작하고 다음 작업을 막지 않는다면 유지
  - 문서에는 “필수 최적화”가 아니라 “I/O 격리와 main-thread 적용 경계를 위한 선택”으로 기록
  - 프로젝트를 처음부터 다시 만든다면 메인 스레드의 bounded nonblocking polling부터 시작
  - 실제 프레임 지연이나 처리량 문제가 확인될 때 전용 스레드로 승격

  지금 와서 단순히 코드가 복잡해 보인다는 이유만으로 되돌리면, 다시 connect 상태·polling 위치·프레임당 처리량·Level 전환 중 수신 처리 등을 재설계해야 합니다. 이미 안정화된 구조를 다시 흔드는 비용이 더 클 수 있습니다.

  그래서 결론은 “잘못 선택했다”보다는 다음 표현이 가장 정확해 보여요.
  > 현재 요구에는 조금 이른 구조였지만, 네트워크 스레드와 게임 스레드의 책임 및 수명 문제를 명시적으로 다루는 선택이었다. 다음번에는 단일 연결 MVP라면 main-thread polling으로 시작하고, 측정된 필요가 있을 때 스레드를 도입한다.

  이 정도면 변명처럼 들리지 않으면서도, 당시 선택과 그로부터 얻은 판단 기준을 모두 설명할 수 있습니다.
