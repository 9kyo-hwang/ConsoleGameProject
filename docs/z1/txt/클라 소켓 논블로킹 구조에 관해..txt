### 왜 localhost인데 즉시 실패하지 않고 2초 넘게 멈출까요?

  일반적으로는 로컬 루프백(127.0.0.1)에서 포트가 닫혀 있으면 OS가 즉시 TCP RST(Reset) 패킷을 반환하여 0ms 만에 실패해야 정상입니다.

  하지만 **Windows 10/11의 Windows Defender 방화벽(WFP)**이나 보안 드라이버는 닫힌 포트로 들어오는 연결 요청에 대해 RST를 즉시 주지 않고 패킷을 무시(Silent Drop)하는 정책을 자주 씁니다.

  1. _socket = Socket::CreateTcp()로 생성된 소켓은 기본적으로 블로킹(동기) 소켓입니다.
  2. 메인 스레드에서 _socket.Connect(endpoint)를 호출합니다.
  3. OS의 TCP 스택은 SYN 패킷을 보냈는데 응답이 없자, 패킷이 유실된 줄 알고 **SYN 재전송(Retransmission 타임아웃 약 1초 + 1초 = 약 2.1초)**을 시도합니다.
  4. 이 2.1초 동안 메인 스레드가 ::connect() 시스템 콜 안에서 완전히 멈춰버립니다(Freeze).
  5. 메인 스레드가 멈춰 있으니 Engine::Tick()도, 키보드 입력도, 화면 렌더링도 모조리 멈춥니다.
  6. 2.1초 뒤 타임아웃 에러를 내며 connect()가 끝나면 비로소 함수가 풀리면서 SetNoticeMessage("서버에 연결할 수 없습니다.")가 뜹니다.
  ──────
  ### 어떻게 해결할 수 있을까요?

  메인 스레드가 멈추지 않게 하려면 소켓 연결(Connect) 작업을 메인 스레드가 아니라 '백그라운드 스레드'에서 처리하도록 넘겨주면 완벽하게 해결됩니다.

  현재 NetworkClient.cpp:64-103의 구조:

  • 메인 스레드가 Connect()를 수행하고 ➔ 성공해야 스레드를 띄움 (_thread = std::thread(...))

  개선 방향 (가장 권장되는 방식):

  • NetworkClient::Start(endpoint)에서는 Connect()를 부르지 않고, 스레드만 띄우고 즉시 반환합니다.
  • 백그라운드 스레드(NetworkLoop)의 맨 첫 부분에서 _socket.Connect(endpoint)를 수행합니다.
  • 이렇게 바꾸면:
      1. 메인 스레드는 game.ConnectToServer() 호출 즉시 0ms 만에 반환되어 **프레임 멈춤이 0%**가 됩니다.
      2. 타이틀은 부드럽게 State::Connecting 상태로 전환되어 화면에 "Connecting to server..."를 깜빡이며 예쁘게 출력합니다.
      3. 백그라운드 스레드가 뒤에서 2초 동안 connect를 시도하다가 실패하면 _connected = false가 됩니다.
      4. 타이틀 레벨의 OnConnectingServer가 !game.IsServerConnected()를 감지하여 자연스럽게 "서버에 연결할 수 없습니다."를 띄우고 메뉴로 돌아옵니다.


  즉, 지금 구현해 두신 TitleLevel의 State::Connecting 상태 머신 로직은 완벽하며, 소켓의 Connect() 작업이 메인 스레드에 남아 있어서 발생한 문제였습니다!

 ### 1. 현재 코드에서 왜 블로킹이 발생했는가?

  NetworkClient.cpp:71-80을 보시면:

    _socket = Socket::CreateTcp(); // 1. 기본 블로킹 소켓 생성
    if (!_socket.IsValid() || !_socket.Connect(endpoint)) // 2. 👈 블로킹 상태에서 Connect() 실행!
    {
        _socket.Close();
        return false;
    }

    // 3. Connect가 성공한 '이후에야' 비로소 논블로킹으로 변경됨
    if (!_socket.SetNoDelay(true) || !_socket.SetNonBlocking(true))
    {
        _socket.Close();
        return false;
    }

  소켓의 모든 속성은 **"해당 함수를 호출하는 그 순간의 소켓 상태"**를 따릅니다.
  현재 코드는 Connect()가 성공하고 돌아온 뒤에야 비로소 SetNonBlocking(true)를 호출하고 있으므로, Connect()를 수행하는 동안에는 100% 동기(블로킹) 모드로 동작했던 것입니다.
  ──────
  ### 2. Connect() 이전에 SetNonBlocking(true)를 부르면 어떻게 되는가?

  소켓 생성 직후 SetNonBlocking(true)를 먼저 부르면 Connect() 역시 **0ms 만에 즉시 반환(논블로킹)**됩니다.

  하지만 이때 소켓 프로그래밍 특유의 처리 규칙이 필요합니다:

  1. 논블로킹 소켓에 connect()를 호출하면 즉시 반환되면서 **SOCKET_ERROR(-1)**를 반환합니다.
  2. 이때 WSAGetLastError()를 확인하면 에러가 아니라 **WSAEWOULDBLOCK (10035)**이 나옵니다.
      • 이는 "실패했다"는 뜻이 아니라 **"OS가 백그라운드에서 TCP 3-Way Handshake를 진행 중이다"**라는 정상 상태입니다.
  3. 연결이 진짜로 성공했는지 실패했는지는 select()를 돌려 확인해야 합니다:
      • 연결 성공 시: writefds에 소켓이 잡힙니다.
      • 연결 실패 시: exceptfds에 소켓이 잡히거나 getsockopt(SO_ERROR)로 에러가 나옵니다.

  ──────
  ### 3. 해결을 위한 2가지 접근법 비교

  최초 접속 시 메인 스레드가 멈추지 않게 하는 방법은 2가지가 있습니다.

  #### 방식 A: 백그라운드 스레드에서 Connect() 호출 (가장 추천! ⭐)

  어차피 NetworkClient는 NetworkLoop라는 전용 스레드를 이미 가지고 있습니다. 따라서 복잡한 WSAEWOULDBLOCK 상태 머신을 만들 필요 없이, 스레드 함수 안에서 Connect()를 부르게 만드는 것이 훨씬
  직관적이고 버그가 없습니다.

    [메인 스레드]
    Start(endpoint) ──► 스레드 시작 후 즉시 return true! (0ms, 멈춤 없음)
                     └─► TitleLevel은 바로 Connecting 상태로 예쁘게 화면 렌더링 유지

    [네트워크 스레드]
    NetworkLoop() ────► _socket.Connect(endpoint) 실행 (블로킹되어도 백그라운드라 상관없음!)
                     ├─► 성공 시: _connected = true ➔ 루프 진입
                     └─► 실패 시: _connected = false ➔ 스레드 종료

  #### 방식 B: 순수 논블로킹 Connect + select

  1. _socket = Socket::CreateTcp();
  2. _socket.SetNonBlocking(true); (먼저 호출!)
  3. _socket.Connect(endpoint);
  4. 반환값이 false이고 에러가 WSAEWOULDBLOCK인 경우를 성공적인 시작으로 간주
  5. NetworkLoop의 select()에서 writefds와 exceptfds로 연결 완료 여부를 체크
  ──────
  ### 결론

  • "호출 이전에 세팅해야 하는가?" ➔ 네, 맞습니다. Connect 전에 호출해야 논블로킹으로 시작됩니다.
  • "최초 접속 때 블로킹은 어쩔 수 없는가?" ➔ 아닙니다.
      • NetworkClient::Start에서 스레드를 먼저 띄우고 스레드 안에서 Connect()를 수행하도록 위임하면, 메인 스레드는 단 0.001초도 멈추지 않고 매끄러운 60 FPS 화면을 유지할 수 있습니다!
