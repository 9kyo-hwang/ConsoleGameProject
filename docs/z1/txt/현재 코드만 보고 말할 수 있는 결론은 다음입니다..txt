현재 코드만 보고 말할 수 있는 결론은 다음입니다.

  - 실제로 검증된 동접은 문서상 2클라이언트 수준입니다.
  - _sessions에는 명시적인 전체 동접 상한이 없습니다.
  - 하지만 모든 클라이언트가 같은 Room에 있으면 Snapshot의 4KB 제한 때문에 최대 226명이라는 하드 상한이 있습니다.
  - 실사용 한계는 그보다 먼저 단일 IO thread의 Tick·Snapshot 생성·직렬화·completion 처리에서 나타날 가능성이 큽니다.

  ### 1. 세션별 Snapshot 생성이 가장 유력합니다

  BroadcastWorldSnapshot() (Z1Server/Server.cpp:453)은 20Hz마다 모든 세션에 대해 각각 다음 작업을 합니다.

  각 Session
  → 해당 playerId 기준 BuildSnapshot()
  → packet 직렬화
  → Session send queue 등록

  그런데 BuildSnapshot() (Z1Server/OverworldSimulation.cpp:303)은 호출할 때마다 전체 컬렉션을 순회합니다.
  - 전체 Player		N
  - 전체 Enemy		M
  - 전체 Projectile	K
  - 포함된 결과를 다시 정렬 O(NlogN)

  모든 N명이 같은 Room에 있다면 세션 N개 각각이 Player N명을 순회하고 정렬하므로 대략: N × (N 순회 + N log N 정렬)
  즉, 동접 증가에 따라 CPU 비용과 송신량이 거의 제곱으로 증가합니다. => N^2logN

### 2. 같은 Room은 패킷 크기로 226명이 한계입니다

  현재 Player 하나의 Snapshot 크기는 18바이트이고 전체 패킷 제한은 4096바이트입니다. 헤더는 (2+2 = 4)바이트, WorldSnapshot 고정 크기는 (4+2+2+2 = 10)바이트.
  적과 투사체가 없다면: Snapshot 크기 = 14 + 18 × 같은 Room Player 수
    플레이어, 적, 투사체 모두 있다면: 4 + 10 + 18 x 플레이어 수 + 19 x 적 수 + 14 x 투사체 수

  TCP/IP 오버헤드와 다른 패킷은 제외한 값입니다.

  새 Player는 적이 없는 Start Room에 들어가므로 227번째 Player가 입장하면 Snapshot 직렬화가 실패하고, BroadcastWorldSnapshot() (Z1Server/Server.cpp:453)의 현재 정책상 실패한 Session을 닫게 됩니다.

  적이 6마리 있는 Room에서는 Player 상한이 약 220명으로 줄고, 투사체가 존재하면 더 낮아집니다. -> 적 공격 쿨타임 2초, 투사체 지속시간 2초라 투사체는 동시에 6개 존재 가능. 따라서 14 + 18 x 215 + 19 x 6 + 14 x 6 = 4082

 ### 3. 단일 IO thread에 모든 일이 모입니다

  Server::IOLoop() (Z1Server/Server.cpp:197) 하나가 다음을 모두 담당합니다.
  - 새 Session 등록
  - Recv/Send completion 처리
  - packet dispatch
  - 20Hz simulation
  - Snapshot 생성과 직렬화
  - CombatEvent 및 경로 디버그 전송
  - 종료 Session 제거

  따라서 Snapshot broadcast가 길어지면 completion 처리가 밀리고, completion이 밀리면 send queue가 증가하며, 다음 Tick도 늦어지는 연쇄가 생길 수 있습니다.

  전체 프로세스 CPU가 낮아 보여도 IO thread 하나가 코어 하나를 100% 사용하고 있을 수 있으므로, 프로세스 전체 CPU보다 스레드별 CPU 사용률을 봐야 합니다.

  ### 4. EnemyPathDebug 패킷 수

  현재 서버는 F3 표시 여부와 관계없이 매 Tick마다 관심 Room의 Enemy 경로를 각 Session에 별도 패킷으로 전송합니다.

  Enemy가 6마리라면 한 Session이 한 Tick에 받을 수 있는 패킷은 대략:

  Snapshot 1개
  + EnemyPathDebug 최대 6개
  + CombatEvent

  MaxQueuedSendPackets = 64 (Z1Server/Session.h:62)는 바이트나 시간 기준이 아니라 패킷 개수 기준입니다. 따라서 코드 주석의 “약 3.2초 이상 밀리면 종료”는 Snapshot만 초당 20개 보낼 때의 계산이고, 경로 디버그가 함께 쌓이면 훨씬 빨리 64개에 도달할 수 있습니다.

  ### 5. 활성 Room이 늘어나면 AI 비용도 증가합니다

  Moblin은 이동 가능한 Tick마다 16×11 Room에서 A*를 실행합니다. 또한 가장 가까운 Player를 찾을 때 전체 Player를 순회합니다.
  클라이언트를 여러 Room에 골고루 배치하면 Snapshot 크기는 줄지만:
  - 활성 Room 증가
  - 활성 Enemy 증가
  - Player 탐색 증가
  - A* 실행 증가

  때문에 simulation CPU가 새로운 병목이 될 수 있습니다.

  ## 무엇을 측정해야 하는가

  “접속이 유지된다”만으로 성공을 판단하면 부족합니다. 서버에 최소한 다음 계측이 필요합니다.
  - 현재 연결/Enter 완료 Session 수
  - 초당 accept, disconnect, recv/send completion 수
  - Tick 실행 시간 평균·p95·p99·최댓값
  - Tick 시작 지연 시간
  - catch-up Tick 횟수와 MaxCatchupTicks 초과 후 시간 재조정 횟수
  - Snapshot 생성·직렬화 시간
  - 초당 Snapshot 수와 송신 바이트
  - Session별 send queue 현재 크기와 high-water mark
  - queue 64개 초과로 닫힌 Session 수
  - A* 호출 횟수와 누적 실행 시간
  - _acceptedSockets, _sessions, Player 수
  - 종료 후 남은 Session·Player·handle 수

  로그는 패킷마다 찍지 말고 1초 단위로 집계해야 합니다. 패킷별 콘솔 출력 자체가 병목이 될 수 있습니다.

  클라이언트 부하 생성기에서는 다음을 측정합니다.
  - connect/Enter 성공률과 소요 시간
  - 수신한 serverTick의 연속성
  - Snapshot 도착 간격 p50·p95·p99
  - 초당 수신 패킷과 바이트
  - 예상하지 않은 연결 종료 수
  - protocol/framing 오류
  - 입력 전송 후 위치 변화가 관찰될 때까지 걸린 시간

  현재 Input packet의 sequence가 Snapshot에 되돌아오지 않으므로 정확한 입력 RTT는 직접 측정하기 어렵습니다. 우선은 Snapshot 간격과 server tick 누락으로 충분합니다.

  ## 권장 테스트 시나리오

  한 번에 모든 문제를 섞지 말고 다음 순서가 좋습니다.

  1. Idle reader
      - 접속하고 Enter한 뒤 Snapshot을 계속 읽기만 함
      - 1, 10, 25, 50, 100, 150, 200, 220, 226, 227명 순으로 증가
      - 같은 Start Room의 최악 조건 확인

  2. Input load
      - 방향 변경을 초당 10~20회 전송
      - 별도로 공격 입력을 집중적으로 전송
      - recv completion과 packet dispatch 병목 확인

  3. Room 분산
      - 클라이언트를 여러 Room에 분산
      - 같은 Room Snapshot 제곱 증가와 활성 Room AI 비용을 비교

  4. Slow reader
      - 일부 클라이언트가 Snapshot을 천천히 읽거나 아예 읽지 않음
      - 느린 클라이언트만 queue 상한으로 제거되는지 확인
      - 정상 클라이언트의 Tick과 Snapshot이 영향을 받지 않는지 확인

  5. Connect churn
      - 일정 수가 반복적으로 connect → Enter → disconnect
      - _sessions, Player, handle, 메모리가 누적되지 않는지 확인

  6. Soak test
      - 임계치의 약 70~80% 부하를 30분 이상 유지
      - 메모리와 handle 증가, 장기 Tick 지연 확인

  기존 tools/test-z1-enter.ps1:1은 protocol 정확성 검사에는 적합하지만, 여러 PowerShell 프로세스를 띄우는 방식은 클라이언트 쪽 부하가 커서 서버 한계 측정에는 적합하지 않습니다. 스트레스 테스트에는 한 프로세스에서 여러 비동기 연결을 관리하는 전용 load client가 필요
  합니다.

  ## “처리 가능 동접” 판정 방법

  예를 들어 다음 기준을 모두 만족하는 최대 N을 측정된 처리 가능 인원으로 정의할 수 있습니다.
  - Enter 성공률 100%
  - 예상하지 않은 disconnect 0
  - Tick 실행 시간 p99가 25ms 이하
  - 50ms Tick deadline 초과와 강제 시간 재조정 0
  - Snapshot 도착 간격 p99가 100ms 이하
  - send queue 최대치가 64에 닿지 않음
  - IO thread가 코어 하나의 70~80% 이하
  - 접속 종료 후 Session, Player, handle, 메모리가 기준치로 복귀

  각 단계는 최소 3회 반복하고, 통과한 최대치보다 20~30% 낮은 값을 운영 여유가 있는 동접으로 보는 것이 안전합니다.

  현재 코드만으로 예상하면 첫 병목 후보는 순서대로 다음입니다.
  1. 같은 Room의 4KB Snapshot 상한
  2. 세션별 BuildSnapshot()·정렬·직렬화
  3. Snapshot과 EnemyPathDebug에서 발생하는 WSASend completion 수
  4. 단일 IO thread의 Tick과 completion 경쟁
  5. 여러 활성 Room의 Player 탐색과 A*

  실제 숫자는 아직 측정되지 않았으므로 “몇 명까지 문제없다”고 말할 단계는 아닙니다. 첫 테스트 목표는 Start Room 기준 100명 → 200명 → 226명에서 20Hz가 유지되는지 확인하는 것이 가장 정보량이 클 것 같습니다.
