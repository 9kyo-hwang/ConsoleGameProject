    → Session::Send(packet)
    → _sendQueue.push_back(packet)
    → 전송 중이 아니면 PostSend()
    → WSASend(overlapped)
    → 나중에 IOCP send completion
    → IOLoop의 HandleSend(bytesTransferred)

1. Session::Send(packet)

  항상 먼저 완성된 패킷을 _sendQueue 뒤에 넣습니다.
  - _sendPending == true이면: 이미 WSASend가 진행 중이므로, 새 전송을 시작하지 않고 queue에만 쌓습니다.
  - _sendPending == false이면: queue의 맨 앞 패킷 전송을 시작하기 위해 PostSend()을 호출합니다.

  2. PostSend()

  PostSend()은 queue를 pop하지 않습니다. queue 맨 앞 패킷의 아직 전송되지 않은 구간을 가리키는 WSABUF를 만들고 WSASend()를 호출합니다.
  성공 또는 WSA_IO_PENDING이면 _sendPending = true가 됩니다. 즉 “현재 front 패킷은 OS의 비동기 송신 완료 통지를 기다리는 중”이라는 뜻입니다.

  _sendQueue: [ Snapshot A, Snapshot B, Combat C ]
                 ^
                 현재 WSASend가 보내는 front
  _sendPending: true

  3. 이후 IOCP send completion

  IOLoop이 completion을 하나 꺼냈고 그것이 GetSendOverlapped()와 같다면 HandleSend(bytesTransferred)를 호출합니다.
  여기서 세 경우로 나뉩니다.
  - 전송 실패 또는 bytesTransferred == 0
      - HandleSend() 실패 → CloseSession()
  - 부분 전송
      - front 패킷은 pop하지 않음
      - _sendOffset만 증가
      - 같은 front의 남은 바이트를 PostSend()로 다시 WSASend()
  - front 패킷 전체 전송 완료
      - pop_front()
      - _sendOffset = 0
      - queue가 비어 있지 않으면 다음 front에 PostSend()
      - 비었으면 _sendPending == false 상태로 대기

  예를 들어 A, B, C 순으로 queue에 들어왔다면:

  Send(A) → [A] → WSASend(A), pending
  Send(B) → [A, B] → A가 pending이므로 B는 대기
  Send(C) → [A, B, C] → C도 대기

  A send completion
    → A 전송 완료면 pop
    → [B, C]
    → 즉시 WSASend(B), pending

  B가 부분 전송되었다면
    → B는 유지, offset만 증가
    → WSASend(B의 남은 부분), pending

  B가 완전히 전송되면
    → pop
    → [C]
    → WSASend(C), pending

  따라서 이 구조의 보장 사항은 세션당 “동시에 outstanding 상태인 WSASend는 최대 하나”라는 점입니다. 그 하나가 완료된 뒤에만 다음 패킷 또는 부분 전송의 다음 구간을 올립니다.

 제가 말한 “즉시”는 A의 send completion을 ioThread가 처리하는 같은 호출 흐름 안에서, 별도 Tick이나 다음 Send() 호출을 기다리지 않고 PostSend()를 호출한다는 뜻입니다. B가 실제 네트워크로 완료되는 시점이 즉시라는 뜻은 아닙니다.

  흐름은 이렇게 됩니다.

  ioThread
    → Session::Send(A)
    → WSASend(A) 시작
    → _sendPending = true

  ioThread
    → Session::Send(B), Session::Send(C)
    → 이미 pending이므로 queue에만 추가
    → [A, B, C]

  커널
    → A의 비동기 WSASend 완료
    → IOCP completion port에 "A send 완료" 통지 적재

  ioThread
    → GetQueuedCompletionStatus()에서 A completion을 받음
    → Session::HandleSend(A의 전송 바이트 수)
    → A pop
    → queue에 B가 남았음을 확인
    → 같은 ioThread에서 PostSend()
    → WSASend(B) 시작

  즉 IOCP가 B를 자동으로 보내 주는 것은 아니고:

  1. 커널이 A 완료를 IOCP에 알림
  2. ioThread가 그 알림을 꺼냄
  3. HandleSend() 내부가 다음 queue 항목을 보고
  4. 그 자리에서 PostSend() → WSASend(B)를 호출

  하는 구조입니다.

  그리고 B가 부분 전송되었다면 A를 pop하던 것과 달리 B는 queue front에 그대로 두고, 같은 HandleSend() 호출 안에서 남은 바이트를 대상으로 다시 PostSend()합니다.

  현재는 Session::Send, HandleSend, PostSend 모두 IOLoop의 단일 ioThread만 실행한다는 전제라서, send queue에 mutex 없이도 순서와 _sendPending 상태를 관리할 수 있습니다.
